# Site da Escola Superior de Guerra (ESGFAA)

Três partes no mesmo repositório:

| Parte | Pasta | Endereço |
|---|---|---|
| Site público (React + Vite) | `src/` | `https://cahuala.github.io/esgfaa/` |
| Painel de administração (tema Color Admin) | `src/admin/`, `admin/index.html` | endereço secreto (ver abaixo); no computador: `localhost:5173/admin/` |
| Portal académico (estudantes e docentes) | `src/portal/`, `portal/index.html` | `…/portal/` (botão "Portal Académico" do site) |
| API (Express + PostgreSQL com Prisma, arquitetura DDD) | `api/` | onde a alojar (ver abaixo); detalhes em [api/README.md](api/README.md) |

O site funciona sem a API: usa os conteúdos de `src/data/`. Com a API ligada, passa a mostrar o que se edita no painel, e ativa gostos, comentários e contagem de visualizações.

## Correr no computador

Precisa do Node.js 24 ou mais recente e do Docker (para o PostgreSQL).

```bash
# 0. PostgreSQL e tradutor LibreTranslate (uma vez; ficam a correr em segundo plano,
#    portas 5434 e 5005; o tradutor descarrega os modelos de língua no primeiro arranque)
docker compose up -d

# 1. API (terminal 1)
cd api
npm install
cp .env.example .env      # opcional em desenvolvimento
npm run migrar            # cria/atualiza as tabelas (migrações do Prisma)
npm run dev               # http://localhost:3001

# 2. Site e painel (terminal 2, na raiz)
npm install
echo "VITE_API_URL=http://localhost:3001" > .env.local
npm run dev               # site: http://localhost:5173  ·  painel: http://localhost:5173/admin/
```

No primeiro arranque a API:
- copia para a base de dados os conteúdos atuais de `src/data/` e as imagens de `src/assets/`;
- cria o administrador `admin@esgfaa.gov.ao` (ou `ADMIN_EMAIL`) com a palavra-passe de `ADMIN_PASSWORD`; sem ela, gera uma palavra-passe aleatória e mostra-a **uma única vez** no terminal. O painel pede que a mude ao entrar.

Para voltar aos conteúdos originais (mantém utilizadores e registo): `cd api && npm run seed -- --forcar`.

Quem ainda tem a base antiga em SQLite (`api/dados/esgfaa.sqlite`) copia tudo para o PostgreSQL com `cd api && npm run importar-sqlite` (só corre numa base vazia).

## Testes automatizados

```bash
npm run test:api        # API: testes de unidade e integração (domínio, segurança, RBAC, conteúdos, ficheiros…)
npm test                # site e painel: componentes e funções (Vitest + Testing Library)
npm run test:e2e        # ponta-a-ponta com o Chrome: entrar no painel, publicar uma notícia, vê-la no site, gostar e comentar
npm run test:tudo       # lint + todos os anteriores
```

Os testes da API usam o PostgreSQL do `docker compose` (cada teste num esquema próprio, apagado no fim); os ponta-a-ponta arrancam uma API e um site próprios (portas 3101 e 5174) com uma base de dados descartável. No GitHub, os testes correm em cada pull request e **antes de cada publicação**: se algum falhar, o site não é publicado. Cobertura: `npm run test:cobertura` (na raiz e em `api/`).

## Portal académico

Em `/portal/` (botão "Portal Académico" do site). Entra-se com o **e-mail da Escola**; a palavra-passe inicial é o próprio e-mail e o portal obriga a mudá-la na primeira entrada. Usa o mesmo tema do painel (Color Admin, com a identidade da Escola): barra lateral com o perfil e as cadeiras, dashboard com widgets e gráficos, linha do tempo no percurso académico, modo claro e escuro.

- **Portal no telemóvel:** o portal instala-se como uma aplicação (ícone no ecrã principal, abre em ecrã inteiro e mais depressa) e envia **avisos** — notas publicadas, avisos, trabalhos, correções, mensagens e lembretes de prazo — mesmo com o portal fechado, no telemóvel ou no computador (Web Push, sem aplicação de loja nem serviço a contratar). Para quem usa é um só cartão na página de entrada, com **Instalar** e **Receber avisos** (no iPhone, a indicação de como adicionar ao ecrã principal), e um interruptor no perfil para ligar ou desligar neste aparelho. Tocar no aviso abre o portal no sítio certo. O servidor cria sozinho as chaves dos avisos (ou usam-se `VAPID_PUBLIC_KEY` e `VAPID_PRIVATE_KEY`).
- **Estudante — a minha turma e a sala de aula:** ao entrar, o estudante vê a sua **turma** (nome, ano letivo, colegas), "continuar onde parou", as cadeiras da turma em cartões com o progresso e o botão **Entrar na sala de aula**, e ao lado as aulas de hoje, o que há para fazer e os avisos. Na **sala de aula** de cada cadeira os capítulos estão à direita: clicar num capítulo abre a lista dos seus itens (com o que já fez assinalado) e mostra o capítulo ao meio; clicar num item abre a aula ao meio — PDF no leitor, vídeo, página, pasta, ligação, trabalho, questionário, sondagem —, com "anterior / seguinte" e o caminho Sala de aula › Capítulo › Item. No telemóvel, a aula vem primeiro e os capítulos por baixo. O docente continua com a página da cadeira e o modo de edição, e com **Ver como estudante** abre a mesma sala tal como os estudantes a veem (sem as atividades escondidas; trabalhos e questionários só em pré-visualização).
- **Estudante:** painel antigo em /painel (números, gráfico das notas do ano, progresso no curso, aulas de hoje, prazos, avisos), **percurso académico** (todos os anos frequentados em linha do tempo, com notas finais, horas concluídas e média das aprovadas), cadeiras com programa, materiais (os **PDF abrem no mesmo leitor da revista, os vídeos e o áudio tocam e as imagens veem-se dentro do portal**, também nas pastas; os vídeos do YouTube ficam incorporados; Word, PowerPoint e Excel descarregam-se), avisos, trabalhos (entrega de ficheiros), notas e presenças; boletim de notas em matriz (disciplinas × 1.ª prova, 2.ª prova, MAC, exame, recurso, nota final e situação), para imprimir; horário semanal; avisos da Administração Escolar; pedidos de documentos (declarações, certificados) e perfil.
- **Página da cadeira como no Moodle:** secção geral (avisos, fórum, programa) e **capítulos** com os materiais, trabalhos e questionários, cada um com o seu estado (feito, entregue, nota); à direita o índice da cadeira, o progresso, as próximas datas, os docentes e o fórum. O docente liga o **modo de edição** para criar, ordenar, esconder e apagar capítulos e para "Adicionar atividade ou recurso" (ficheiros em lote com barra de envio, ligações, vídeos, trabalhos, questionários). Separador **Participantes**. O painel inicial tem linha temporal, mini-calendário, cadeiras acedidas recentemente e cartões das cadeiras com progresso.
- **Questionários completos:** 9 tipos de pergunta (escolha única e múltipla, verdadeiro/falso, resposta curta sem contar acentos nem maiúsculas, numérica com tolerância, correspondência com crédito parcial, **preencher lacunas** e **ordenar** com crédito parcial, dissertação corrigida à mão); **provas**: palavra-passe dada na sala (nunca chega ao estudante), N perguntas por página e navegação **só para a frente** (o servidor não aceita respostas de páginas já passadas), **comentário conforme a nota** e **exceções por estudante** (outro fecho, mais tempo ou mais tentativas, com aviso ao estudante); **banco de perguntas** do docente por categorias, reutilizável entre questionários e cadeiras; perguntas e opções baralhadas e N perguntas sorteadas por tentativa; correção manual com comentário (a nota sai quando todas as dissertações estiverem corrigidas e o estudante é avisado); **estatísticas** por pergunta (facilidade e distribuição das escolhas), média e mediana.
- **Trabalhos completos:** entrega com até 10 ficheiros, com texto escrito no portal, ou ambos; grelha de avaliação (rubrica) com pontos por critério convertidos em nota de 0 a 20; **correção no PDF dentro do navegador** (caneta, realce, comentários, ✓ e ✗, em quatro cores, com desfazer e borracha): o portal gera o PDF corrigido, que o estudante vê no leitor, e guarda as anotações para o docente as voltar a editar; ficheiro corrigido devolvido só ao autor; prorrogação do prazo para um estudante (é avisado, e não recebe o lembrete do prazo geral). **Fluxo de correção:** com **correção anónima**, o docente vê "Participante 1, 2…" (numeração baralhada) em vez dos nomes; com **notas publicadas de uma vez** (implícito na anónima), os estudantes não veem nota, comentário nem ficheiro corrigido, a nota não entra na pauta e ninguém é avisado até o docente carregar em **Publicar as notas** — aí todos as veem ao mesmo tempo, recebem o aviso e os nomes voltam a aparecer. Uma entrega já corrigida não pode ser substituída enquanto as notas não forem publicadas.
- **Livro de notas ligado às atividades:** cada componente da pauta (1.ª prova, 2.ª prova, exame, recurso) pode ser lançada à mão ou **calculada** a partir de trabalhos e questionários com pesos (média ponderada; sem entrega depois do prazo conta 0); fica em dia sozinha quando chega uma correção ou uma tentativa. Pauta **exportável para Excel** (portal e painel).
- **Cópia de segurança da cadeira e importação do Moodle:** em "Importar e cópias" (modo de edição da cadeira), o docente **descarrega a cópia de segurança** da cadeira num só ficheiro .zip (capítulos, materiais com os ficheiros, trabalhos com grelha, questionários com as perguntas, sondagens, avaliação por pares, datas, programa e composição das notas; sem entregas, notas nem dados dos estudantes) e **restaura-a** nessa ou noutra cadeira. Também **importa cursos do Moodle (.mbz)**: os tópicos passam a capítulos (o tópico 0 é a secção geral) e entram as páginas, rótulos, ligações, ficheiros, pastas e trabalhos; o que não tem equivalente (questionários, fóruns, H5P, SCORM…) aparece numa lista no fim. O que a cadeira já tem fica como está; os questionários restaurados ficam por publicar. O ficheiro é tratado como não confiável: tamanho máximo depois de descomprimido (1 GB, contra "bombas" de compressão), cada campo validado, páginas sem scripts, ligações só http/https e ficheiros confirmados pelo conteúdo.
- **Novo ano letivo:** a Administração Escolar copia as cadeiras de uma turma para outra (cria as que faltam e copia capítulos, materiais com cópia dos ficheiros, trabalhos, questionários, datas, programa e composição das notas, com as datas avançadas um ano), ou uma cadeira de cada vez; o docente usa "Importar de outra cadeira" no modo de edição. Entregas, notas, fórum e presenças não se copiam.
- **Restrições e conclusão:** cada atividade pode ser **escondida**, ter uma **data de abertura** (também por capítulo) e **condições** — "só abre depois de concluir X", com nota mínima opcional no trabalho ou questionário. O estudante vê a atividade fechada com o motivo; a API recusa abri-la, entregar ou responder. Com todas as atividades concluídas, o estudante obtém o **certificado de conclusão** da cadeira (pronto a imprimir), com um código que qualquer pessoa verifica em `/portal/#/verificar`. As restrições copiam-se com as cadeiras (datas avançadas, condições sobre as atividades novas).
- **Livro e Lição** (como os do Moodle): o **Livro** junta capítulos e subcapítulos com índice próprio, lê-se capítulo a capítulo e imprime-se inteiro; o docente escreve-o no portal. A **Lição** é uma aula guiada: páginas de matéria com perguntas pelo meio, em que cada opção tem um comentário e leva a uma página (a seguinte, outra, a mesma ou o fim). O caminho e a nota (primeira resposta a cada pergunta, de 0 a 20) são decididos no servidor — as respostas certas nunca chegam ao navegador do estudante —; a lição conta como concluída ao chegar ao fim, pode repetir-se (fica a melhor nota) e o docente vê os resultados de cada estudante.
- **Conteúdos interativos SCORM e H5P:** o docente carrega um **pacote SCORM** (1.2 ou 2004, o .zip com o imsmanifest.xml) ou um **conteúdo H5P** (.h5p com as bibliotecas, por exemplo do H5P.com ou do Lumi), e o estudante faz a aula numa moldura dentro do portal (com ecrã inteiro). O SCORM recebe o nome do estudante, guarda onde parou (retoma no mesmo sítio) e envia o estado e a nota; o H5P envia a nota quando o estudante responde. Aprovado ou concluído conta para o progresso da cadeira (e para os emblemas); o docente vê os **resultados da turma** (estado, nota de 0 a 20, tempo). O pacote é servido pela API num endereço assinado e temporário (8 horas), que só abre para quem tem acesso à atividade; o .zip original fica guardado e entra nas cópias de segurança (noutro servidor, o pacote abre-se outra vez a partir dele).
- **Ferramentas externas (LTI 1.3):** a Administração Escolar regista no painel (Ferramentas externas) cada ferramenta — laboratório virtual, simulador, biblioteca digital… — com os endereços que esta indica, e copia para a ferramenta os dados do portal (emissor, JWKS, endereço de autorização, Client ID e Deployment ID). O docente junta-a à cadeira como atividade ("Ferramenta externa"); o estudante carrega em "Abrir a ferramenta" e entra numa janela nova já identificado, sem outra palavra-passe: o portal assina (RS256, chave criada sozinha em `dados/lti.json`) quem é, o papel (estudante ou docente), a cadeira e a atividade. Só se enviam o nome e o e-mail se a ferramenta estiver marcada para isso. O endereço de retorno tem de estar registado, e o pedido vale 10 minutos. Em produção, `PUBLIC_URL` tem de estar definido (é o emissor e não pode mudar depois de configurar as ferramentas). Faça cópia de segurança do `dados/lti.json`.
- **Emblemas:** ganham-se sozinhos, a partir do progresso (sem nada a configurar): **Primeiros passos** (a primeira atividade de cada cadeira), **Capítulo concluído** (todas as atividades de um capítulo), **Cadeira concluída** e **Sempre a tempo** (todos os trabalhos da cadeira, pelo menos dois, entregues dentro do prazo). O estudante vê-os em **Os meus emblemas** (os ganhos, e os por ganhar com o que falta) e num cartão em "A minha turma" com o próximo a ganhar.
- **Mais recursos:** **Página** (texto rico escrito no portal, com títulos, tabelas e vídeos), **Pasta** (vários ficheiros num só recurso; o docente junta e retira), **Videoconferência** (dia, hora e duração; numa **sala do portal** — o portal cria uma sala Jitsi com nome difícil de adivinhar e a sessão abre dentro da página, com o nome de quem entra, ecrã inteiro e "abrir noutra janela" — ou numa ligação de outro serviço (Zoom, Teams, Meet); o botão "Entrar" abre 15 minutos antes e a sessão aparece nas próximas datas), **Sondagem** (uma pergunta de escolha única ou múltipla, anónima ou não, com resultados aos estudantes depois de responderem, depois do fecho ou nunca) e **avaliação dos docentes**: a Administração Escolar lança na turma um inquérito pedagógico anónimo por docente e cadeira (oito afirmações de 1 a 5 e dois comentários); a base de dados não liga respostas a estudantes, o docente só vê os resultados agregados depois do fecho e com pelo menos 3 respostas, e não pode esconder nem apagar a sua avaliação.
- **Grupos:** separador "Grupos" em cada cadeira; o docente cria grupos à mão ou ao acaso (N estudantes por grupo ou N grupos) e escolhe os membros — cada estudante está num só grupo por cadeira. **Trabalhos em grupo:** uma entrega por grupo, que qualquer membro faz ou substitui (os colegas são avisados); a correção, a nota (também na pauta calculada), o progresso e os ficheiros valem para todo o grupo e só para ele.
- **Relatórios e administração:** registo de acessos dos estudantes (página da cadeira, materiais, ficheiros, trabalhos, questionários, inquéritos e fórum; a mesma página em 5 minutos conta uma vez); separador **Relatórios** do docente com a participação de cada estudante (acessos, último acesso com alerta a partir de 7 dias, atividades abertas, entregas, questionários, fórum; exportável para Excel), o uso de cada atividade e o registo de acessos filtrável por estudante. A Administração Escolar **importa estudantes de Excel (.xlsx) ou CSV** na turma: a folha é lida no navegador, a pré-visualização diz o que acontece a cada linha (conta nova, só matrícula, já matriculado ou erro) e só depois se grava.
- **Fórum completo:** tópicos de discussão e de **perguntas e respostas** (abertos pelo docente; o estudante só vê as respostas dos colegas depois de responder), até 3 **anexos** por mensagem, **resposta certa** marcada por quem perguntou ou pelo docente, **seguir** o fórum inteiro ou um tópico (e deixar de seguir), **pesquisa** nos assuntos, mensagens e respostas, e edição das próprias mensagens nos primeiros 30 minutos (o docente modera sempre). Os avisos abrem diretamente o tópico.
- **Indicadores académicos** (painel da Administração Escolar, por ano letivo): estudantes ativos, **estudantes em risco** com os motivos (menos de 75% de presenças, negativas nas provas, recurso ou reprovação, 14 dias sem entrar no portal), **pautas em atraso** (notas por lançar 15 dias depois da data da prova, com os docentes), cadeiras sem docente, e por turma e cadeira a aprovação, a média final e a assiduidade.
- **Avaliação por pares** (como o "Workshop" do Moodle): o docente define a grelha, o prazo de entrega e o de avaliação; no fim da entrega cada estudante recebe ao acaso N trabalhos de colegas para avaliar (nunca o seu; anónimo se se quiser); no fim vê as avaliações recebidas e a nota (média dos pares, que o docente pode rever). Conta para o progresso, as restrições, a cópia de cadeiras e a pauta calculada (quem não entregou fica com 0).
- **Glossário e wiki da cadeira:** o glossário tem termos por ordem alfabética, com pesquisa e índice de letras; os estudantes propõem e o docente aprova. A wiki tem páginas escritas por todos no editor de texto, ligações entre páginas com [[Título]], histórico de versões, aviso quando duas pessoas gravam ao mesmo tempo e reposição de versões pelo docente.
- **Pesquisa e calendário externo:** caixa de pesquisa no cabeçalho do portal, que procura nas cadeiras de quem pesquisa (cadeiras, materiais e páginas, trabalhos, questionários, fórum, glossário, wiki e avisos), com excertos e o termo realçado; o estudante não encontra o que está escondido. O calendário pode ser **assinado** no Google Calendar, Outlook ou telemóvel (iCal, endereço pessoal secreto que se pode renovar), com aulas, provas, entregas, questionários, videoconferências e prazos da avaliação por pares, nas horas de Luanda.
- **Documentos da Administração Escolar** (imprimir ou guardar em PDF, com cabeçalho oficial e espaço para assinaturas; exportação para Excel): pauta de cada cadeira, **pauta da turma** (estudantes × cadeiras, média e situação no ano), **folha de presenças** (aulas registadas e colunas em branco), **lista de presenças para a prova** com espaço para assinar, **histórico académico** de cada estudante e **certificado de conclusão do curso** (com código verificável em `/portal/#/verificar`).
- **Pessoal e Quadros e Administração Escolar:** a Repartição de Pessoal e Quadros (papel próprio) **regista** estudantes e docentes — dados pessoais (posto, ramo, NIP) e conta do portal, um a um ou a partir de Excel/CSV — e repõe palavras-passe. A Administração Escolar **não regista ninguém**: consulta o registo e escolhe quem matricular nas turmas (pesquisa com escolha múltipla, ou folha com e-mail ou número de estudante), quem inscrever em cadeiras e que docentes alocar.
- **Inquéritos de satisfação (institucionais):** a Administração Escolar prepara inquéritos sobre a Escola — a partir de um modelo (serviços da Escola, avaliação do curso) ou em branco, com perguntas de escala 1 a 5, escolha (uma ou várias) e resposta livre —, escolhe a quem se destinam (estudantes, docentes ou todos; turmas concretas) e até quando, e lança: o portal avisa cada destinatário e mostra o inquérito em **Inquéritos**. As respostas são anónimas (a base guarda quem respondeu, para não responder duas vezes, separado do que respondeu e só com o dia); depois de lançado, as perguntas já não mudam. Resultados com médias e distribuição, exportáveis para Excel. Os inquéritos (os da Escola e os das cadeiras) têm o **aspeto de um formulário do Google**: cartão de cabeçalho com a faixa da cor da Escola, um cartão por pergunta, "* obrigatória", escala linear de 1 a 5 entre "Discordo totalmente" e "Concordo totalmente", resposta aberta numa linha, "Enviar" e "Limpar formulário"; ao enviar com perguntas por responder, essas ficam a vermelho e a página vai até à primeira. O editor no painel segue o mesmo modelo (título, apresentação, cartões com o tipo à direita, duplicar, mover, apagar, adicionar opção/pergunta) e tem **Pré-visualizar**, que mostra o inquérito como o vê quem responde.
- **Biblioteca:** o bibliotecário (papel próprio) cataloga obras — livros, teses, monografias, TFC, artigos e revistas, com autores, assuntos, editora, ISBN (o dígito de controlo é verificado), cota e resumo —, regista exemplares com código (tombo, gerado ou lido por código de barras) e estado, e junta uma versão digital em PDF, para todos ou só para docentes. Ao balcão empresta e devolve pelo código do exemplar: 14 dias e até 3 livros para estudantes, 30 dias e até 5 para docentes, 2 renovações (só antes do prazo e só se derem mais tempo); quem tem livros em atraso não leva outros. Sem multas. Listas de emprestados, atrasos e histórico (exportáveis), aviso aos leitores em atraso e exportação do catálogo em Dublin Core (OAI-DC). No portal, a biblioteca abre como uma sala com estantes de madeira (novidades, para ler já, teses e TFC, uma por assunto) e as capas das obras — a imagem carregada pelo bibliotecário ou, sem ela, uma capa desenhada (clássica, moderna, académica com o emblema da Escola, revista). A ficha mostra o livro em 3D, onde está e se está disponível; o digital lê-se dentro do portal, numa página própria, como uma página web: **não se descarrega** (o servidor envia-o sempre para ver, nunca como anexo, e o leitor não tem botão de descarga), não se imprime (Ctrl+P sai em branco), não se seleciona nem copia, e cada página leva em marca de água o nome de quem lê — dissuasores, porque nenhum site impede uma fotografia ao ecrã; o leitor **reserva** o livro que escolheu (a biblioteca separa-o e avisa; ao emprestar, a reserva fica atendida) e, em "Os meus livros", vê prazos, renova e cancela reservas.
- **Integridade académica (anti-plágio):** cada trabalho entregue no portal (PDF, Word ou texto escrito) é lido e comparado, em segundo plano, com os outros trabalhos entregues, as obras digitais da biblioteca e um repositório de referência (teses e TFC antigos, carregados pela Administração Escolar). O texto é normalizado (sem acentos, maiúsculas nem palavras vazias) e partido em sequências de 5 palavras; cada documento guarda uma amostra dessas sequências (winnowing), o que permite encontrar depressa as fontes candidatas e garante apanhar qualquer passagem igual com 8 ou mais palavras com conteúdo. Citações entre aspas e a lista de referências não contam. O docente vê a percentagem na lista de entregas e abre o relatório: medidor, fontes com cores, texto com os trechos assinalados e comparação lado a lado com a fonte. Também pode verificar um documento avulso (o ficheiro não fica guardado, só o texto). A Administração Escolar vê todas as análises, verifica documentos e gere o repositório. Os estudantes não veem os relatórios. Com a chave do **Brave Search** (`BRAVE_API_KEY`), cada análise pesquisa também na internet algumas frases do trabalho (8 por omissão, espalhadas pelo texto), lê as páginas encontradas (HTML ou PDF, só endereços públicos, com limites de tempo e tamanho) e compara-as como mais uma fonte, com ligação no relatório. A **utilização de IA** é avaliada sempre por indicadores locais (regularidade das frases e dos parágrafos, fórmulas típicas de assistentes, diversidade de vocabulário) e, com a chave da Anthropic (`ANTHROPIC_API_KEY`), pelo Claude, que dá uma probabilidade, a justificação e os parágrafos suspeitos, assinaláveis no texto. É sempre um indicador para o docente, nunca uma prova. Sem chaves, a pesquisa na internet e o Claude ficam desligados e o relatório diz isso.
- **Todo o sistema em várias línguas (PT, EN, FR, ES):** site, portal académico e painel. No site, o seletor está no cabeçalho (ou `?lang=en` no endereço); no portal e no painel, na barra de cima. A escolha fica guardada no navegador e vale para os três. A interface (menus, botões, formulários, mensagens de erro da API, datas) está em dicionários: `src/i18n/textos*.js` (site) e `src/i18n/app/*.js` (portal e painel), carregados só quando se escolhe outra língua. Um teste confirma que cada texto tem as 3 traduções, sem marcadores `{…}` inventados nem traduções contraditórias. Os documentos oficiais impressos pelo painel (pautas, certificados, históricos, listas de presença) ficam sempre em português. Mudar de língua recarrega a página (também no portal e no painel, cujos endereços têm `#`), e as páginas de entrada têm os botões PT · EN · FR · ES.
- **Dados dos painéis na língua escolhida:** fora do português, o que vem da base de dados e aparece no portal e no painel (nomes das cadeiras, capítulos, atividades, avisos, notificações, títulos das obras…) vai ao mesmo tradutor automático do servidor (`POST /api/portal/traduzir` e `/api/admin/traduzir`). Cada texto é traduzido uma só vez e fica guardado (tabela `textos_traduzidos`), servindo a todos. Os nomes com posto ("Cap.-Ten. Pedro Neto") nunca são traduzidos, nem os campos de escrita, os editores, os e-mails e os documentos oficiais. Na primeira vez que um texto aparece, chega em português e muda passados alguns segundos.
- **Tradução automática dos conteúdos:** quando se publica uma notícia, artigo, evento, curso, pessoa ou página, o servidor traduz para as outras três línguas e publica a tradução, marcada como automática (o site mostra o aviso "Tradução automática do original em português"). Ao arrancar, completa o que estiver em falta ou desatualizado. O tradutor é o **LibreTranslate** (gratuito, no próprio servidor: serviço `tradutor` do `docker compose`, `LIBRETRANSLATE_URL=http://127.0.0.1:5005`) ou, com `ANTHROPIC_API_KEY`, o Claude (melhor redação). No painel, o quadro **Traduções** de cada conteúdo mostra o estado por língua; a janela de tradução põe cada texto original ao lado da tradução, assinala o que mudou no original e permite corrigir, guardar em rascunho ou publicar. Uma tradução revista à mão deixa de ser automática e só os textos alterados no original voltam a ser traduzidos. As traduções ficam numa tabela própria, separada do original. O site publicado sem API (GitHub Pages) usa as traduções que vêm com ele em `src/data/traducoes.json`; depois de rever traduções no painel, atualize-o com `npm run traducoes:exportar` (com a API a correr).
- **Admissão:** não há candidaturas online. O registo dos oficiais admitidos é feito pela Repartição de Pessoal e Quadros (painel → Pessoal e efetivos); o site explica o processo em Cursos → Admissão (proposta do ramo, análise, provas, registo e matrícula), sem formulários nem prazos de candidatura.
- **Revista da Escola:** no painel (Revista), cada número é um PDF com número, tema, data, apresentação, capa e sumário (título, autor e página de cada artigo). No site, em **Revista**, qualquer visitante, sem registo, vê o número mais recente em destaque e a estante com os outros, e lê cada um num **leitor de PDF dentro da página** (pdf.js) com aspeto de página web — as páginas correm umas atrás das outras na própria página, sem moldura, e o texto seleciona-se e pesquisa-se como num site —, zoom, ir para a página, ecrã inteiro, teclado, descarga, também no telemóvel; o sumário abre o leitor diretamente no artigo. Sem capa carregada, a capa é a primeira página do PDF. Os números traduzem-se como os outros conteúdos (os nomes com posto, como "Cor. Ana Baptista", nunca se traduzem). Os dois números que vêm com o site são edições de demonstração.
- **Inscrição em cadeiras e conclusão do curso:** a Administração Escolar inscreve estudantes em cadeiras de outra turma (atraso, repetição, equivalência); o inscrito vê a cadeira e entra na pauta, presenças, trabalhos e avisos. Nas turmas de finalistas lança o **trabalho de fim de curso** (tema, orientador, júri, defesa e nota). O curso conclui-se com todas as unidades curriculares aprovadas (vale o melhor resultado de cada código) e o TFC aprovado; a média final conta o TFC como mais uma unidade curricular (`CONCLUSAO_CURSO` em `api/src/dominio/academico/conclusao/percurso.js`).
- **Interação:** no modo de edição da cadeira, as atividades arrastam-se entre capítulos e os capítulos arrastam-se para mudar a ordem (as setas e o seletor continuam para o telemóvel); confirmações e perguntas usam janelas do tema (Esc cancela, Enter confirma) em vez das do navegador, no portal e no painel.
- **Notificações e mensagens:** sino no cabeçalho e página de notificações (material novo, avisos, trabalhos, correções, notas publicadas, respostas no fórum, questionários, datas marcadas, avisos gerais, pedidos tratados), também por e-mail se a conta quiser (preferência no perfil); **lembrete automático 24 h antes do prazo** a quem ainda não entregou; **mensagens privadas** entre docentes e estudantes que partilham uma cadeira.
- **Recursos ao estilo do Moodle:** **fórum** em cada cadeira (tópicos e respostas; o docente fixa, fecha e modera); **calendário académico** mensal com aulas (sem os feriados), provas, exame e recurso marcados pelo docente, entregas de trabalhos, fecho dos questionários e eventos da Administração Escolar; **progresso das atividades** (materiais vistos, trabalhos entregues, questionários feitos), com relatório estudantes × atividades para o docente; **questionários online** de escolha única, múltipla ou verdadeiro/falso, com abertura e fecho, tempo limite e tentativas, gravação automática das respostas e correção automática (nota de 0 a 20). O servidor é que controla o tempo: depois do fim só contam as respostas gravadas a tempo, e o estudante nunca recebe as respostas certas antes de entregar.
- **Avaliação (modelo do ensino superior angolano):** MAC = média das duas provas parcelares; MAC ≥ 14 sem prova negativa dispensa do exame (nota final = MAC); os outros vão a exame, com nota final = 40 % MAC + 60 % exame; quem reprova vai a recurso (a mesma fórmula, com o recurso no lugar do exame). Nota final arredondada às unidades; classificação Reprovado (< 10), Suficiente (10–13), Bom (14–16), Muito bom (17–20). Segue o regulamento do ISP Tundavala (art. 19.º–26.º); os números estão juntos em `api/src/dominio/academico/regras.js` (`AVALIACAO`) para os ajustar ao regulamento da Escola. O portal importa a mesma regra, por isso a pauta calcula exatamente como o servidor.
- **Docente:** nas cadeiras onde está alocado (regente ou assistente) publica materiais (ficheiros, ligações, vídeos) e avisos, cria trabalhos e corrige as entregas, lança a pauta em matriz (estudantes × 1.ª prova, 2.ª prova, exame, recurso, com MAC e nota final calculadas ao escrever) e publica cada coluna quando quiser, regista aulas (sumário) e presenças.
- **Administração Escolar (no painel):** turmas (ano letivo e ano curricular), matrículas (cria a conta do estudante), contas de docentes, cadeiras (1.º semestre, 2.º semestre ou anual) criadas sem docente e **alocação de docentes** depois (regente + assistentes, com horas; página geral da carga horária), **programa da cadeira** escrito no editor ou em documento, **pautas** (lança e publica notas como o docente), **calendário académico** (eventos da Escola ou de uma turma, épocas de exames, feriados), horários, pedidos de documentos (com anexo do documento pronto) e avisos do portal. Papel "Repartição de Administração Escolar" (permissões `academico.ver`, `academico.gerir` e `academico.notas`).

Os materiais, entregas e documentos ficam numa pasta **privada** (`dados/privado`) e só são entregues pela API a quem tem acesso (inscrito na cadeira, dono da entrega, docente da cadeira). As sessões do portal e do painel são independentes. Variável `EMAIL_DOMINIO_ESCOLA` (por omissão `esgfaa.gov.ao`) define o domínio aceite nas contas.

Dados de demonstração (só em desenvolvimento): `cd api && npm run semear-portal` — cria uma turma, 4 cadeiras, 2 docentes (`miguel.santos@`, `ana.baptista@esgfaa.gov.ao`) e 4 estudantes (`joao.fernandes@`, `maria.costa@`, `pedro.neto@`, `sofia.lima@esgfaa.gov.ao`); a palavra-passe inicial de cada um é o próprio e-mail.

## Painel de administração

- **Conteúdos:** notícias, artigos, eventos, cursos e corpo docente, com imagens, galerias, vídeos (YouTube ou ficheiro) e PDF.
- **Páginas do site:** página inicial, Institucional, admissão aos cursos e Contactos.
- **Comentários:** são publicados de imediato; o painel permite apagá-los.
- **Formulário de contacto:** as mensagens do site ficam no painel, em **Mensagens do site** (caixa de entrada com contador no menu, "Por tratar / Todas / Respondidas", pesquisa, "Responder por e-mail" já com a mensagem citada, marcar como respondida, notas internas e apagar). Com `CONTACTOS_EMAIL` e `SMTP_URL`, cada mensagem chega também por e-mail. Tem proteção contra robôs (campo escondido) e limite de 3 mensagens em 10 minutos por endereço. Sem API (GitHub Pages), o formulário abre o programa de e-mail com a mensagem já escrita. Permissões `contactos.ver` e `contactos.gerir` (o editor-chefe tem as duas).
- **Utilizadores** (só administradores): criar contas, mudar o papel, desativar.
- **Registo de atividades** (só administradores): entradas, tentativas falhadas, criações, edições (com os campos alterados), remoções e envios de ficheiros, com data, utilizador e IP.

- **Publicidade:** banners com posição no site, datas, e contagem de impressões e cliques.
- **Estatísticas:** visitantes, páginas vistas, online agora, páginas mais vistas, origens, dispositivos e horas (sem cookies nem IP).
- **Papéis e permissões (RBAC):** cada papel tem uma grelha de permissões (ver, criar, editar, apagar, publicar) por área, editável no painel. A API verifica todas as permissões.

Papéis iniciais: **Administrador** (tudo, não editável), **Editor-chefe** (publica conteúdos, páginas, publicidade e comentários), **Redator** (escreve rascunhos de notícias, artigos e eventos), **Moderador** (comentários) e **Analista** (estatísticas). Quem não tem a permissão *publicar* só guarda rascunhos e não altera conteúdos já publicados.

## Sistema de Gestão de Pessoal (rede interna)

Sistema próprio da Repartição de Pessoal e Quadros, **separado do site e do portal**: tem API própria (`api-pessoal/`, porta 3002), base de dados própria (`esgfaa_pessoal`) e aplicação própria (`pessoal/`). **Não vai para a internet**: a API recusa qualquer pedido que não venha das redes internas da Escola, e a publicação no GitHub Pages retira a aplicação.

- **Militares dos três ramos** (Exército, Força Aérea e Marinha — com os nomes de posto de cada ramo e a equivalência entre eles) e **pessoal civil**. Daqui saem os docentes, os estudantes e os restantes funcionários.
- **Carreiras segundo a Lei n.º 13/18** (Lei das Carreiras dos Militares das FAA). O sistema verifica cada **promoção** (tempo mínimo no posto do art. 97.º, modalidade do art. 98.º, cursos do art. 52.º, posto limite do quadro especial dos arts. 84.º–95.º, exclusões dos arts. 50.º, 63.º, 99.º e 103.º; distinção e título excepcional dos arts. 57.º e 58.º), cada **graduação** (arts. 64.º–67.º), cada **nomeação** (arts. 18.º–20.º), as **licenças** (arts. 31.º–41.º), a **reserva e a reforma** (arts. 110.º, 111.º e 114.º) e as **listas de antiguidade** (arts. 26.º e 29.º). Cada condição aparece com o artigo.
- **Propostas** de promoção, graduação, nomeação, exoneração e progressão (civis). A Escola não faz despachos: prepara a proposta, imprime as **fichas de proposta** (com fotografia, a situação actual e as condições da lei) e a **síntese biográfica**, e envia ao escalão superior. Quem não cumpre a lei não segue.
- **Extractos**: quando chega o extracto (promoção, nomeação, graduação, exoneração, reserva, reforma), carrega-se o PDF; o sistema lê o texto e encontra os militares pelo NIP e pelo nome (e junta os da proposta). Confirma-se e aplica-se: as fichas mudam, fica no histórico, a proposta fica concluída e o extracto é anexado ao **processo individual** de cada um.
- **Processos individuais** (como no SIGP): n.º PI-NNNNN, localização da pasta (estante › prateleira › posição), estado, documentos digitalizados (BI, extractos, certificados…), lista do que falta actualizar e etiqueta da lombada.
- **Importação por Excel** (inserir novos ou actualizar por NIP), com simulação antes de gravar e correspondência exacta de posto, ramo, unidade e cargo; **fotografias em lote** (nome do ficheiro = NIP). **Consulta do BI** na base de dados do Estado (a mesma API do SIGP, `BI_API_KEY`), que preenche a ficha.
- **Empregados domiciliares** dos oficiais superiores e generais, dentro do limite do posto (Major/Ten.-Coronel 1, Coronel 2, Brigadeiro/Ten.-General 3, General 4); não contam como trabalhadores civis.
- **Orgânica e planeamento** (como no SIGPFAN): árvore da Escola com o efectivo previsto e existente por categoria em cada unidade (contando as subunidades), subunidades e cargos com a fotografia de quem os ocupa.
- **Painel** com mais de 20 gráficos (ramo, categoria, posto, escalões por ramo, forma de serviço, situação, faixa etária, habilitações, quadros especiais, unidades, províncias, reserva por ano, ocupação do quadro orgânico, licenças, propostas, movimentos dos últimos 12 meses…). **Tudo é clicável** e abre a lista já filtrada.
- **Todas as tabelas** com fotografias, pesquisa, ordenação, paginação, linhas clicáveis e exportação para **Excel e PDF**. Cada exportação fica registada na auditoria. O painel tem também gráficos sobre as **mulheres** (por ramo, categoria, posto e vínculo).
- **Perfil do militar**: dados pessoais e militares, fotografia, carreira (o que falta para a promoção), histórico, cursos, graduações, licenças e propostas. Imprime-se em PDF (ficha individual).
- **Quadro orgânico**: unidades, cargos, posto de cada cargo, lugares e quem os ocupa.
- **Ligação ao portal (num só sentido)**: quando se regista ou altera um docente ou estudante com e-mail, a API interna envia à API do portal **só** o nome, o e-mail, o posto, o ramo, o NIP, o telefone e a unidade, num pedido assinado (HMAC-SHA256 com data, recusado se tiver mais de 5 minutos). O portal cria ou atualiza a conta; quem sai da Escola fica com a conta desativada. O portal nunca pede nada ao sistema de pessoal.
- **Expediente**: as áreas enviam e recebem documentos pelo sistema (protocolo EXP-AAAA-NNNN, anexos, classificação, prazo), confirmam a recepção, encaminham e arquivam; se houver original em papel, cada passo regista quem o levou e quando chegou.
- **Mensagens internas**: conversa geral da Escola, a de cada unidade, conversas directas e grupos, com anexos e aviso de mensagens por ler.
- **Utilizadores e papéis próprios**: administrador, chefe (envia propostas e regista as respostas), operador, consulta e **utente** — cada militar ou civil da Escola, que entra com o NIP e só vê o expediente da sua área, as mensagens e a sua ficha («Criar contas para todos» gera as palavras-passe iniciais num PDF). Bloqueio da conta após 5 tentativas falhadas; auditoria de entradas, consultas de fichas, alterações e exportações.

Pôr a correr (no servidor interno da Escola):

```bash
cd api-pessoal
npm install
# .env: DATABASE_URL, JWT_SECRET (32+ caracteres), ADMIN_EMAIL, ADMIN_PASSWORD,
#       HOST (IP da rede interna), REDES_INTERNAS (ex.: 10.10.0.0/16), APP_DIR=../dist/pessoal
npm start                   # aplica as migrações e arranca na porta 3002
npm run semear              # (opcional) dados de demonstração
```

A aplicação constrói-se com `npm run build` na raiz (fica em `dist/pessoal`) e é servida pela própria API interna (`APP_DIR`). Em desenvolvimento: `npm run dev` em `api-pessoal/` e abrir `http://localhost:5173/pessoal/`.

**Ligação ao portal em produção** (os docentes e estudantes registados no sistema interno passam a ter conta no portal):

1. Gere uma chave: `openssl rand -base64 48`. Ponha-a em `INTEGRACAO_CHAVE` **nos dois servidores** (a mesma).
2. No servidor interno (`api-pessoal/.env`, ver `api-pessoal/.env.example`): `PORTAL_API_URL` = endereço da API do portal (ex.: `https://api.esgfaa.gov.ao`).
3. A rede interna tem de deixar o servidor interno **sair** por HTTPS (porta 443) até à API do portal. O portal nunca entra na rede interna: o pedido é sempre de dentro para fora.
4. Os dois servidores com a **hora certa** (NTP): pedidos com mais de 5 minutos de diferença são recusados (protecção contra repetição).
5. Em «Ligação ao portal» (sistema interno): «Reenviar todos» a primeira vez. Depois, cada docente ou estudante criado ou alterado segue sozinho em poucos segundos; se o portal estiver em baixo, tenta de novo de minuto a minuto.

As contas novas no portal entram com o e-mail como palavra-passe inicial (o portal obriga a mudá-la). Os e-mails têm de ser do domínio da Escola (`EMAIL_DOMINIO_ESCOLA`); os que não forem aparecem como erro na página «Ligação ao portal». Se o e-mail de alguém mudar, a conta do portal é a mesma (reconhecida pelo número da conta). Sem chave, a entrada no portal não existe.

> As carreiras e categorias do **pessoal civil** seguem o regime geral da função pública e estão marcadas «a confirmar» até a Escola indicar a legislação que aplica.

## Segurança e acessos simultâneos

**Testes de intrusão** (`api/tests/integracao/ataques.test.js`, `seguranca.test.js`, `sessao.test.js`, `rbac.test.js`, `ficheiros.test.js`), que correm em cada publicação. Cada ataque tem de ser recusado:
- **sessões falsificadas:** token sem assinatura (`alg: none`), assinado com outra chave, com o utilizador trocado, do painel usado no portal e vice-versa, e depois de sair;
- **ver o que é de outros (IDOR):** cadeira de outra turma, ficheiros e entregas de colegas, pautas e relatórios por estudantes ou por docentes de outras cadeiras;
- **subir de privilégios:** estudante a dar-se nota, a criar atividades ou a mexer na pauta; docente a mexer na cadeira de outro;
- **injeção:** SQL na pesquisa e nos parâmetros; scripts, eventos (`onerror`), ligações `javascript:` e `iframe` estranhos nas páginas (retirados); caminhos fora da pasta (`../../`);
- **ficheiros perigosos:** página web ou programa com nome de PDF, SVG com script;
- **palavras-passe à força:** a conta bloqueia ao fim de 5 falhas (15 minutos), há limites por endereço, e a mensagem é a mesma para e-mail inexistente e palavra-passe errada;
- **cabeçalhos de segurança** (helmet), CORS só para os sites autorizados, corpos grandes recusados, erros sem detalhes internos.

**Centro de segurança** (painel → Segurança → Centro de segurança; permissões `seguranca.ver` e `seguranca.gerir`, só o administrador as tem por omissão), atualizado de 10 em 10 segundos:
- **estado geral** (tudo normal / atenção / possível ataque) pelos últimos 5 minutos, com os motivos;
- **saúde do servidor:** ligado há quanto tempo, base de dados (ligada e em quantos ms responde), pedidos por minuto, tempo de resposta médio e de 95 % dos pedidos, erros do servidor, processador, memória da API e disco;
- **gráficos** da última hora (pedidos e eventos suspeitos por minuto) e das últimas 24 horas (eventos por hora e por tipo);
- **ao vivo:** cada evento suspeito com a hora, o tipo, o endereço e o que pediu — palavra-passe errada, conta bloqueada, demasiados pedidos, acesso negado, procura de ficheiros de ataque (`.env`, `.git`, `wp-admin`, `phpmyadmin`…), tentativas de injeção (SQL, script, `../`), erros do servidor;
- **endereços mais ativos** (15 min) com o botão **Bloquear**, e a lista dos **bloqueados** (desbloquear, ou bloquear à mão um endereço por 1 hora a 30 dias). Um endereço bloqueado recebe 403 em tudo (site, portal e painel);
- **bloqueio automático:** um endereço que, em 5 minutos, faz 20 procuras de ficheiros de ataque ou 5 tentativas de injeção fica bloqueado 24 horas (os erros de palavra-passe não bloqueiam o endereço, porque numa rede partilhada, como a da Escola, bloqueariam todos — para esses há o bloqueio da conta e os limites por endereço);
- **modo vigilância:** ecrã inteiro e escuro, para deixar num ecrã de parede, com **alarme sonoro** opcional quando o nível passa a "possível ataque";
- **alerta por e-mail** (no máximo um a cada 30 minutos) com `SEGURANCA_EMAIL` e `SMTP_URL`.

Os eventos guardam-se juntos por minuto, tipo e endereço durante 90 dias (sem palavras-passe nem dados pessoais); os números de tráfego ficam em memória (últimas 24 horas desde o arranque).

**Dependências:** `npm audit` sem vulnerabilidades no site/painel e na API (a ferramenta do Prisma trazia versões com falhas do `deepmerge-ts` e do `mysql2`, que o `package.json` da API força para versões corrigidas).

**Teste de carga** (`cd api && npm run carga`; `ESTUDANTES=300 SEGUNDOS=30 npm run carga` para mais): monta uma Escola de teste numa base temporária (não toca na real), com uma turma de 100 estudantes, e mede cada cenário durante 15 s. Resultados num Mac (M-series), API e PostgreSQL no mesmo computador:

| Cenário | Ligações ao mesmo tempo | Pedidos por segundo | Tempo médio | Erros |
|---|---|---|---|---|
| Site: página inicial | 120 | ≈ 16 700 | 0,14 s | 0 |
| Portal: estudantes a abrir a cadeira | 100 | ≈ 280 | 0,35 s | 0 |
| Portal: "A minha turma" | 100 | ≈ 650 | 0,15 s | 0 |
| Portal: notificações | 100 | ≈ 2 400 | 0,04 s | 0 |
| Docente: lista de entregas | 20 | ≈ 450 | 0,04 s | 0 |
| Entrar no portal (palavra-passe) | 50 | ≈ 120 | 0,41 s | 0 |

Cada ligação pede sem parar; uma pessoa real abre uma página a cada poucos segundos, por isso estes números correspondem a milhares de pessoas a usar o sistema ao mesmo tempo. Entrar é de propósito mais lento (a palavra-passe é verificada com scrypt, o que também atrasa quem tenta adivinhá-la). O conteúdo do site fica 10 segundos em memória (e é apagado a cada alteração no painel): antes disso, a página inicial aguentava ≈ 800 pedidos por segundo e falhava com 200 visitantes ao mesmo tempo. Com os limites ligados, 2000 pedidos seguidos de um só endereço dão 300 respostas e 1700 recusas (429). Em produção, suba `DB_POOL` (ligações à base de dados, 10 por omissão) se houver muitos docentes e estudantes ao mesmo tempo.

## Pôr a API online

A API precisa de uma base **PostgreSQL** (gerida, como Neon, Supabase ou Render, ou num VPS) e de um **disco persistente** para as imagens carregadas (`api/dados/uploads`). No arranque, `npm start` aplica as migrações pendentes.

Variáveis de ambiente obrigatórias em produção (ver `api/.env.example`):

| Variável | Para quê |
|---|---|
| `NODE_ENV=production` | modo de produção |
| `JWT_SECRET` | segredo longo e aleatório para as sessões (`openssl rand -hex 32`) |
| `ADMIN_PASSWORD` | palavra-passe do primeiro administrador (mínimo 10 caracteres, com letras e números) |
| `PUBLIC_URL` | endereço público da API, ex.: `https://api.esgfaa.gov.ao` |
| `CORS_ORIGINS` | sites autorizados, ex.: `https://cahuala.github.io` |
| `DATABASE_URL` | ligação ao PostgreSQL, ex.: `postgresql://utilizador:senha@servidor:5432/esgfaa` |
| `DATA_DIR` | pasta persistente para os ficheiros carregados |
| `SEGURANCA_EMAIL` | quem recebe o alerta quando o Centro de segurança deteta um possível ataque (precisa do `SMTP_URL`) |
| `CONTACTOS_EMAIL` | e-mail que recebe um aviso de cada mensagem do formulário de contacto do site (precisa do `SMTP_URL`; sem ele, as mensagens ficam só no painel, em **Mensagens do site**) |
| `JITSI_URL` | servidor Jitsi das salas de videoconferência do portal (por omissão `https://meet.jit.si`, gratuito, mas que limita as salas dentro de outros sites e pede a quem abre a sala que entre com uma conta; para uso real, instale um servidor Jitsi da Escola — é gratuito — e ponha aqui o endereço) |
| `DB_POOL` | ligações simultâneas ao PostgreSQL (10 por omissão; ex.: 30 num servidor com muitos utilizadores) |
| `SMTP_URL` | servidor de e-mail para as notificações, ex.: `smtps://portal%40esgfaa.gov.ao:SENHA@smtp.servidor.ao:465` (sem ele, as notificações ficam só no portal) |
| `EMAIL_REMETENTE` | remetente dos e-mails, ex.: `Portal Académico ESG <portal@esgfaa.gov.ao>` |
| `PORTAL_URL` | endereço do portal, para as ligações nos e-mails, ex.: `https://cahuala.github.io/esgfaa/portal/` |
| `TRUST_PROXY=1` | se estiver atrás de um proxy (Render, Nginx…) |

Com Docker (construir a partir da raiz, porque a carga inicial lê `src/data`):

```bash
docker build -f api/Dockerfile -t esgfaa-api .
docker run -p 3001:3001 -v esgfaa-dados:/app/api/dados --env-file api/.env esgfaa-api
```

Depois, no GitHub: **Settings → Secrets and variables → Actions → Variables → New variable**, nome `API_URL`, valor o endereço da API. Na publicação seguinte, o site e o painel passam a usá-la.

### Endereço secreto do painel

O painel **não** é publicado em `/admin`. Em **Settings → Secrets and variables → Actions → Secrets → New repository secret**, crie `ADMIN_PATH` com um nome difícil de adivinhar (só letras minúsculas, números e hífenes, 8 a 64 caracteres, ex.: `gestao-x7k4q9`). O painel fica em `https://cahuala.github.io/esgfaa/<ADMIN_PATH>/`. Sem esse secret, o painel não é publicado. Para mudar o endereço, altere o secret e volte a publicar.

O endereço secreto é só uma camada extra: a proteção real está na API (palavras-passe fortes, bloqueio da conta após 5 tentativas falhadas, sessões que se podem terminar, permissões verificadas em cada pedido e registo de atividades). Ver [api/README.md](api/README.md#segurança).

Faça cópias de segurança regulares da base de dados (`pg_dump`), das pastas `api/dados/uploads/` e `api/dados/privado/` e dos ficheiros `api/dados/vapid.json` (as chaves dos avisos no telemóvel) e `api/dados/lti.json` (a chave das ferramentas externas).
